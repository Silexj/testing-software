# Лабораторная работа 6

Нагрузочное тестирование OpenBMC и публичных API с помощью Locust.

Ветка: [lab6-locust](https://github.com/Silexj/testing-software/tree/lab6-locust/lab6).

## Установка

Из корня репозитория, Python 3.11+:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r lab6/requirements-analysis.txt
export BMC_URL=https://127.0.0.1:2443
export BMC_USERNAME=root
read -rsp 'Пароль OpenBMC: ' BMC_PASSWORD; echo
export BMC_PASSWORD
# Только для самоподписанного сертификата учебного QEMU:
export BMC_VERIFY_TLS=false
```

Для запуска без построения PNG достаточно `requirements.txt`.
Стенд QEMU запускается скриптом `tools/start_openbmc.sh` из `main`.
Перед нагрузкой дождаться готовности OpenBMC и появления `PowerState` в системе.
Пароль не записывается в исходный код, метаданные прогона или Git.

## Два класса пользователей

`OpenBMCUser`: отдельная Redfish-сессия на пользователя, задачи `BMC system`
(вес 3) и `BMC PowerState` (вес 2), пауза 1–3 с. Оба сценария читают ресурс
`/redfish/v1/Systems/system`, но проверяют разные данные и имеют разные метки
статистики. Проверяются HTTP 200 и JSON; запрос питания проверяет допустимое
значение `PowerState`. После остановки сессия удаляется. Управление питанием
под нагрузкой не выполняется.

`PublicAPIUser`: последовательно читает JSONPlaceholder `/posts` и
`https://wttr.in/Novosibirsk?format=j1`, затем делает паузу 3–5 с.
Проверяются HTTP-код и структура JSON, а не только факт получения ответа.
Погода вызывается по абсолютному URL, так как это другой хост.

В обоих классах используется `catch_response=True`: неправильный JSON и отсутствие
обязательных полей учитываются как ошибки даже при HTTP 200. Тайм-аут запроса — 15 с.
Неожиданный JSON `null` также считается ошибкой.

Дополнительные переменные: `BMC_CA_BUNDLE` (доверенный CA), `BMC_SYSTEM_PATH`,
`PUBLIC_API_URL`, `WEATHER_URL`. По умолчанию используются адреса из задания.
Опция CLI `--host` меняет хост выбранных классов, поэтому отдельные сервисы
проще запускать отдельными прогонами, как в командах ниже.

## Веб-интерфейс

```bash
python -m locust -f lab6/locustfile.py OpenBMCUser \
  --web-host 127.0.0.1 --web-port 8089 \
  --csv lab6/results/web_demo --csv-full-history \
  --html lab6/results/web_demo.html --stop-timeout 20
```

1. Открыть `http://localhost:8089`.
2. Указать Number of users = **10**, Ramp up = **2**, Host = адрес OpenBMC.
3. Нажать Start, наблюдать Statistics, Charts, Failures и Exceptions.
4. Нажать Stop. На узком экране управление находится в меню справа вверху.
5. Сохранить данные через Download Data; затем завершить Locust Ctrl+C.

Для публичного API заменить `OpenBMCUser` на `PublicAPIUser`, задать 1 пользователя
и Host `https://jsonplaceholder.typicode.com`.
Снимки веб-интерфейса находятся в `results/locust_web_*.jpg`.

## Воспроизводимые прогоны без UI

```bash
python lab6/run_profiles.py bmc --users 1 5 10 --duration 30s --spawn-rate 2
python lab6/run_profiles.py public --users 1 --duration 20s --spawn-rate 2
python lab6/analyze_results.py --plot --p95-limit-ms 5000
```

Каждый уровень запускается отдельным процессом. Время включает разгон;
завершение выполняющихся задач и удаление сессий могут увеличить фактическую
длительность. Публичный прогон малый: один пользователь, оба API, паузы между циклами.
Код возврата драйвера ненулевой, если один из прогонов Locust завершился с ошибкой.

## Данные и критерий устойчивости

В `results/` сохранены:

- `*_stats.csv` — периодические снимки стандартного CSV-экспорта Locust;
- `*_final_stats.csv` — итоговая статистика после остановки всех пользователей,
  включая последние ответы и удаление сессий; именно её использует анализ;
- `*_stats_history.csv` — история числа пользователей, RPS и задержек;
- `*_failures.csv`, `*_exceptions.csv` — HTTP/прикладные ошибки и исключения;
- `*.html` — автономные отчёты Locust с интерактивными графиками;
- `*.json` и `*.log` — параметры и протоколы прогона;
- `summary.csv`, `summary.json` — сводка; `bmc_load.png`, `bmc_load.svg` — графики.

Учебный критерий задан до анализа: 0% ошибок, p95 ≤ 5000 мс, достигнуто заданное
число пользователей, выполнены обе операции чтения, Locust завершился без ошибки.
Это выбранный критерий эксперимента, а не гарантированный SLA OpenBMC.
Все агрегированные метрики включают login и logout. p95 берётся из распределения
Locust; процентили разных запросов не усредняются. Locust округляет процентили.
На графике RPS и p95 показаны в скользящем окне 10 с, в сводке — за полный прогон.

## Результаты тестирования

| Цель | Пользователи | Запросы | Среднее, мс | p95, мс | Ошибки | RPS |
|---|---:|---:|---:|---:|---:|---:|
| OpenBMC | 1 | 16 | 204,20 | 390 | 0% | 0,54 |
| OpenBMC | 5 | 70 | 329,38 | 1400 | 0% | 2,34 |
| OpenBMC | 10 | 122 | 744,95 | 2000 | 0% | 4,01 |
| Публичные API | 1 | 8 | 568,91 | 1500 | 0% | 0,51 |

Максимальная устойчивая нагрузка **среди проверенных уровней — 10 пользователей**.
При росте нагрузки задержки увеличиваются. Предел пропускной способности не
достигнут в этом эксперименте; точный максимум и длительная устойчивость
не установлены. 30-секундные прогоны включают разгон, отдельного длительного
прогрева и испытания на выносливость нет. Для физического BMC результаты могут
отличаться от QEMU. Малая выборка публичных API подтверждает работоспособность
сценария, но не характеризует предельную производительность сервисов.

Веб-прогон демонстрирует UI и сохранён отдельно от контрольных профилей.
