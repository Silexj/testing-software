# Лабораторная работа 8

Профилирование OpenBMC Romulus в QEMU: аппаратные счётчики `perf`, показатели
хоста `vmstat`, сетевые метрики `nmon`, память RSS процесса эмулятора.

Ветка: [lab8-profiling](https://github.com/Silexj/testing-software/tree/lab8-profiling).
Работа самостоятельна: Jenkins и код предыдущих веток для запуска не требуются.
Locust-сценарий скопирован из лабораторной 6, commit `cebb22c`, и включён сюда.
Используется только `OpenBMCUser`, без запросов к публичным сервисам.

## Методика

Для каждого варианта параметров запуска создаётся новая рабочая копия исходной
прошивки Romulus `BUILD_ID=20250902012112`. Готовность подтверждается чтением
Redfish и состоянием Off, затем выдерживается 30 с прогрева. Сначала собираются
60 секунд простоя, затем 60 секунд нагрузки: 10 пользователей, разгон 2/с,
чтение системы и PowerState с паузой 1–3 с. Входы и выходы включены в статистику.
Питание хоста остаётся Off. Модель датчиков/PSU из работ 5/7 здесь не требуется:
измеряются ресурсы эмулятора при чтении штатного API.

- `perf stat --no-scale -e cycles:u,instructions:u,cache-misses:u -p PID -- sleep 60`
  измеряет **процесс QEMU на хосте**, а не виртуальные счётчики ARM-гостя.
  Присоединение после загрузки исключает смешивание загрузки ОС с нагрузкой API.
  Суффикс `:u` ограничивает сбор пользовательским кодом: на хосте
  `perf_event_paranoid=2`. Настройки ядра и права системы не изменяются.
- `vmstat -w 1 61` записывает 60 интервалов. Первая строка со статистикой
  с момента загрузки хоста исключается из анализа.
- `nmon -F network.nmon -s 1 -c 61 -p` сохраняет сетевые показатели хоста.
  После начальной инвентаризации ожидается первый снимок; затем запускаются
  остальные измерения. Первый снимок nmon исключается, остаются 60 интервалов.
  Интерфейсы рассматриваются отдельно; их сумма удваивала бы один и тот же
  трафик, проходящий через loopback, Docker bridge и veth.
- `samples.csv` содержит ежесекундный CPU хоста из `/proc/stat`, CPU процесса
  из `/proc/PID/stat` и RSS из того же файла. CPU хоста — доля от всех логических
  процессоров без idle и iowait. CPU QEMU — доля одного логического процессора
  (100% соответствует одному полностью занятому ядру); эти проценты имеют
  разные знаменатели. RSS указан в MiB (2²⁰ байт), а не размер виртуального
  адресного пространства или объём ОЗУ гостя `-m`.

CPU хоста включает генератор Locust и фоновые процессы настольной системы;
его изменения нельзя целиком приписать QEMU. Сеть BMC оценивается отдельно
по Docker-интерфейсу, а не по общему Wi-Fi/VPN-трафику компьютера.

Проверяются два варианта: штатный выбор кэша TCG (`baseline`) и ограничение
`-accel tcg,tb-size=64` (`tb64`). Образ, ОЗУ гостя 256 MiB, нагрузка и интервалы
одинаковы. Оба запуска используют TCG на x86_64 для ARM; KVM не является
заменой TCG для такого сочетания архитектур. Выводы относятся к коротким
последовательным опытам на этом компьютере, без заявления статистической
значимости малых различий скорости.

## Подготовка и запуск

Нужны Linux, Docker, Python 3, Locust/Requests, `perf`, `nmon` и `vmstat`.
Для штатной установки инструментов на Fedora: `sudo dnf install perf nmon procps-ng`.
Альтернатива без изменения системных пакетов: `bash lab8/prepare_tools_fedora.sh`.
Она скачивает официальные Fedora RPM в игнорируемый каталог `.runtime/lab8`
и извлекает только исполняемые файлы. Их системные библиотеки должны быть доступны.

Команды выполняются из корня репозитория:

```bash
git switch lab8-profiling
python3 -m venv .venv-lab8
source .venv-lab8/bin/activate
python -m pip install -r lab8/requirements.txt
docker build -t testing-software-qemu:lab8 -f lab8/Dockerfile lab8
read -rsp 'Пароль OpenBMC: ' BMC_PASSWORD; echo
export BMC_PASSWORD
python lab8/run_profile.py /absolute/path/to/romulus.static.mtd
python lab8/run_profile.py /absolute/path/to/romulus.static.mtd --run-name tb64 --tb-size 64
python lab8/analyze_results.py
```

При локальном извлечении RPM добавить к обеим командам `run_profile.py`:

```bash
--perf "$PWD/.runtime/lab8/binroot/usr/bin/perf" \
--nmon "$PWD/.runtime/lab8/binroot/usr/bin/nmon"
```

Можно передать `--password-file /path/to/local-secret` вместо переменной.
Пароли не сохраняются в результатах или Git. Исходная flash не меняется.
Контейнер QEMU запускается с UID пользователя, без capabilities и без Docker
socket; HTTPS опубликован только на `127.0.0.1:2443`. На время опыта порт
должен быть свободен. Фоновые сборки Jenkins и другой стенд QEMU стоит остановить
на время измерений, затем вернуть в исходное состояние.

Каталоги результатов не перезаписываются. Для нового опыта нужен новый
`--run-name`, например `repeat1`; `--tb-size 64` задаётся только при проверке
ограниченного кэша. Созданный контейнер останавливается и удаляется в `finally`,
включая случай ошибки; его журнал и результат очистки сохраняются.

## Состав результатов

`results/<run>/idle` и `load` содержат команды и исходные `perf.csv`, `vmstat.log`,
`network.nmon`, `samples.csv`. В `load` дополнительно находятся HTML/CSV/log
Locust. `environment.json` фиксирует аргументы запуска, SHA-256 прошивки,
версии инструментов, ядро и PID процесса. `system-before.json` и `system-after.json`
подтверждают состояние OpenBMC, `cleanup.json` — остановку QEMU.

`analyze_results.py` проверяет полноту всех трёх источников профилирования,
положительные аппаратные счётчики, совпадение условий сравнения, 10 пользователей,
0 ошибок HTTP и удаление всех 10 сессий. Для гибридного Intel значения cpu_core
и cpu_atom агрегируются по событию без масштабирования (`--no-scale`);
неактивная PMU может иметь `<not counted>`,
но отсутствие всех измеренных значений события считается ошибкой.

Сводка записывается в `results/summary.json` и `summary.md`, контрольные суммы —
в `results/SHA256SUMS`. График из посекундных данных строится командой
`python lab8/plot_results.py` после `pip install -r lab8/requirements-plot.txt`. После его обновления
повторить анализ для обновления контрольных сумм.

## Фактические результаты

| Вариант / фаза | CPU хоста, % | CPU QEMU, % одного ядра | RSS QEMU, MiB |
|---|---:|---:|---:|
| baseline / простой | 10,09 | 23,05 | 630,22 |
| baseline / нагрузка | 14,34 | 62,78 | 632,45 |
| tb64 / простой | 8,46 | 22,43 | 492,94 |
| tb64 / нагрузка | 11,16 | 58,25 | 492,96 |

Обычный запуск: 301 запрос, p95 400 мс. Вариант с кэшем 64 MiB: 297 запросов,
p95 330 мс. В каждом опыте достигнуты 10 пользователей, ошибок HTTP 0,
все 10 сессий удалены, питание осталось Off, QEMU после опыта остановлен.
Ограничение кэша снизило средний RSS под нагрузкой на **22,1%**.
Разница CPU и времени ответа по одному короткому опыту не доказывает
устойчивого ускорения. Нагрузка на хост включает фоновые процессы и Locust.

Все проверки целостности и полноты измерений в `analyze_results.py` пройдены.
Исходники измерения зафиксированы в commit `e5374c2`, их SHA-256 приведены в
[source-manifest.json](results/source-manifest.json). Данные и график доступны
в [results](results), итоговый [отчёт](Отчёт_Лабораторная_8.docx) — в формате DOCX.

## Демонстрация преподавателю

1. Показать параметры QEMU в `results/baseline/environment.json` и команды
   сбора метрик в `idle/commands.json` и `load/commands.json`.
2. Запустить новый опыт с `--run-name demo`; дождаться сообщений idle/load.
3. Открыть сырой вывод perf, vmstat и раздел NET в файле nmon.
4. Выполнить анализ и показать CPU/RSS до и во время нагрузки, затем HTML Locust.
5. Сравнить baseline и tb64, объяснить разницу между ОЗУ гостя, RSS и кэшем TCG.
